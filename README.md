# 予定フリー在庫数 設計資料

## 1. 結論

> 予定フリー在庫数で並べ替え・絞り込みをしないため、既存一覧の 50 在庫を先に確定し、その 50 件の明細だけを直接集計できる。

- 予定フリー在庫数は、**既存の一覧で決まった 50 在庫について、現在庫と未完了の入出庫明細を直接集計**して求める。事前集計テーブルや非同期処理は追加しない。インフラも変えず、入庫明細と出庫明細にインデックスを 1 本ずつ追加するだけにする。
- 予定日の変更・数量の変更・削除は、明細テーブルの更新だけで次のリクエストに反映される。変更前の日付から予定数を取り消す処理は不要である。
- 50 在庫に値を付与する SQL の p95 は、高密度のデータで PostgreSQL 17.5ms、MySQL 51.8ms だった（6 章）。
- この設計が成り立つ条件、置いた仮定、未検証の事項は **5 章にまとめた**。

## 2. 前提

| 項目 | 前提 |
|---|---|
| 一覧の limit | 50 固定 |
| 1 在庫の明細数の上限（1,000 件） | 完了済みも含めた、入庫と出庫の合算と解釈する |
| 日付の基準 | JST。過去日は対象外 |

**書き込み負荷**：課題の頻度が全体の数字か各社の数字かは不明なので、負荷が高くなるほうに合わせて**各社の数字**と想定する。1,000 社が同時に稼働すると、全体で約 500 件/秒（在庫数量の更新 約 167 件/秒 ＋ 入出庫の作成・更新 約 333 件/秒）になる。全体の数字だった場合は合計 30 件/分で、この想定に収まる（7 章 Q5 で確認する）。

直接集計で増える書き込みのコストは、明細の作成・削除と、status・scheduled_date・quantity の変更時に追加インデックスを更新する分だけである。

## 3. 取得方法

### 3.1 計算式

```
logical_quantity(D) = inventory.quantity
                    + Σ 入庫明細.quantity（未完了 かつ scheduled_date <= D）
                    − Σ 出庫明細.quantity（未完了 かつ (scheduled_date <= D または scheduled_date IS NULL)）
```

- 未完了は、status が `none` または `before` の明細とする。
- 予定日を過ぎても完了していない明細は、`scheduled_date <= D` を満たすため、指定日の値に含まれる。
- 日付未定の出庫は今日から差し引き、日付未定の入庫は含めない。日付が決まるまで、入庫はどの日から使えるかを決められないため。

### 3.2 在庫一覧 API

一覧に出る 50 件は予定フリー在庫数に依存しない。そのため、既存の一覧処理で 50 件を確定してから、その 50 件にだけ値を付与する。

1. 認証済みアカウントの在庫スコープに、既存の検索条件・並び順・ページングを適用し、50 件を確定する（既存の処理のまま）。
2. その 50 件の在庫 id について、予定フリー在庫数を 1 クエリで集計する（付録 A.1）。
3. 既存の `inventories` と `pagination` の形式に `logical_quantity` を加えて返す。

```ruby
# 例（ページングの書き方は既存の実装に合わせる）
ApplicationRecord.transaction(isolation: :repeatable_read) do
  inventories = current_company.inventories.search(params).order(existing_order).page(page).per(50)
  logical = LogicalQuantity.for(company: current_company, inventory_ids: inventories.map(&:id), date: date)
  # inventories の各要素に logical[inventory.id] を付けて、既存の形式で返す
end
```

1 と 2 は同じ REPEATABLE READ のトランザクション内で実行し、同じスナップショットを読む。こうすると、完了処理の前後の状態が混ざらない。

集計では、対象 50 在庫の明細をインデックスから読み、status と予定日の条件に合う数量だけを合計する。読む行は一覧全体で最大 5 万件（50 在庫 × 1,000 件）になる。

### 3.3 推移グラフ API

1 在庫について、現在庫と未完了の明細を 1 文で読み、日付ごとに合計する（付録 A.2）。アプリ側で日付順に累積し、増減のない日を埋めて全日付を返す。補完をサーバー側で行うのは、フロントのロジックを小さく保ち、テストを request spec で完結させるためである。期間は最大 90 日とする。

## 4. 整合性の仕組み

### 4.1 完了処理

現在庫 10、未完了の入庫 5 の明細を完了しても、予定フリー在庫数は完了の前後で 15 のまま変わらない。ただし、次の 2 つのずれが起こりうる。

- 在庫の加算と明細の完了が別々にコミットされると、「現在庫 15 ＋ 未完了 5 ＝ 20」になる。
- 完了処理が数量 5 を読んだあと、別のリクエストが明細を 8 に変更すると、在庫は正しい 18 ではなく 15 になる。

これを防ぐため、1 明細の完了処理は次の順で、1 つのトランザクションで確定する。

```sql
BEGIN;
SELECT inventory_id, quantity, status FROM purchase_item
 WHERE company_id = :company_id AND id = :item_id FOR UPDATE;
-- status が completed なら何もせず終了する（二重完了の防止）
UPDATE purchase_item SET status = 'completed', completed_date = :today
 WHERE company_id = :company_id AND id = :item_id;
UPDATE inventory SET quantity = quantity + :locked_quantity      -- ロックした行の数量（出庫なら減算）
 WHERE company_id = :company_id AND id = :locked_inventory_id;   -- ロックした行の在庫 id
COMMIT;
```

- **編集側**：数量の変更は `WHERE ... AND status <> 'completed'` を付けて実行する。更新件数が 0 件なら、完了済みとして拒否する。
- 完了処理が明細をロックしている間は、数量の変更は待たされ、ロックが解けた後は完了済みとして拒否される。変更が先にコミットされていれば、完了処理は変更後の数量を読む。
- ロックを取る順序は「明細 → 在庫」になる。数量の編集は明細だけ、在庫数量の更新は在庫だけをロックするので、ロックの順序が逆になる組み合わせは生じない。

### 4.2 読み取り先

```mermaid
flowchart LR
    A((Browser)) --> B[ALB] --> C((nginx)) --> D((Rails))
    D -- "明細・在庫の更新（完了処理は 4.1 の手順）" --> P[(DB プライマリ)]
    D -- "一覧・グラフの読み取り" --> P
```

一覧・グラフはプライマリ DB を読む。こうすると、コミット済みの変更が次のリクエストから反映される。SNS / SQS / Lambda / Batch は使わない。

### 4.3 受け入れ条件

**同じ在庫・同じ日付・同じ確定状態なら、一覧とグラフは同じ値を返す。**

例：今日の現在庫 10、明日に入庫予定 5。各行は、この初期状態から 1 つの操作をした結果である。

| 操作 | 今日 | 明日 | 明後日 | 現在庫 |
|---|---:|---:|---:|---:|
| （初期状態） | 10 | 15 | 15 | 10 |
| 入庫予定日を明後日に延期 | 10 | 10 | 15 | 10 |
| 入庫を完了 | 15 | 15 | 15 | 15 |
| 入庫を 2 回完了する | 15 | 15 | 15 | 15 |
| 入庫予定日を NULL に変更 | 10 | 10 | 10 | 10 |
| 日付未定・status が none の出庫 5 を登録 | 5 | 10 | 10 | 10 |
| 上の出庫に明日の日付を設定 | 10 | 10 | 10 | 10 |
| 明細を 8 に変更してから完了 | 18 | 18 | 18 | 18 |
| 完了処理の途中で、明細を 8 に変更しようとする | 15 | 15 | 15 | 15（変更は拒否） |

`bench/acceptance_test.py` は、この表に数量の変更・削除・出庫の完了を加えた 12 ケースを、PostgreSQL と MySQL の両方で検証する。

- status は課題どおり文字列で保持する。
- すべてのケースで、一覧の SQL・グラフの SQL・現在庫を期待値と比較し、1 件でも不一致があれば失敗する。
- 最後の行は、2 本の接続で実際にロックの待ちを発生させて確認する。変更側のセッションが DB 上でロック待ちになったことは、PostgreSQL は `pg_stat_activity`、MySQL は `information_schema.innodb_trx` で観測して記録する。
- 一覧の SQL をわざと壊したコピーで実行し、失敗を検出できることも確認した。

## 6. 計測

| 条件 | PostgreSQL 16（p50 / p95） | MySQL 8.0（p50 / p95） |
|---|---|---|
| 高密度のページ（1 ページ目） | 13.5 / 17.5 ms | 32.0 / 51.8 ms |
| 高密度のページ（最終ページ） | 13.7 / 16.1 ms | 31.0 / 36.9 ms |
| 明細の少ないページ | 0.7 / 1.0 ms | 1.3 / 1.5 ms |

- 50 在庫の id を渡して予定フリー在庫数を付与する SQL（付録 A.1）を、200 回逐次実行した。
- 高密度のページは、1 在庫に入庫・出庫それぞれ 1,000 件、すべて未完了の明細を持つ（課題の上限の 2 倍）。指定日は、未完了の明細がすべて集計対象になる日にした。
- データはメモリに載った状態、単一クライアント、ネットワーク遅延なし、2 vCPU / 7GB の環境で計測した。未検証の事項は 5 章の U1〜U4。上の数値は、遅延の原因を切り分けるときの基準として使う。
- 採用の根拠は、直接集計単体の実測値と、事前集計を持つ場合に必要になる整合性管理のコスト（付録 C）である。方式間の速度差は根拠にしていない（付録 B）。

## 付録 A. SQL

### A.1 一覧：50 在庫への付与

```sql
SELECT t.id,
       t.quantity
       + COALESCE((SELECT SUM(pi.quantity) FROM purchase_item pi
                   WHERE pi.company_id = :company_id AND pi.inventory_id = t.id
                     AND pi.status IN ('none', 'before')
                     AND pi.scheduled_date <= :date), 0)
       - COALESCE((SELECT SUM(di.quantity) FROM delivery_item di
                   WHERE di.company_id = :company_id AND di.inventory_id = t.id
                     AND di.status IN ('none', 'before')
                     AND (di.scheduled_date <= :date OR di.scheduled_date IS NULL)), 0)
         AS logical_quantity
FROM inventory t
WHERE t.company_id = :company_id AND t.id IN (:inventory_ids)   -- 3.2 の手順 1 で確定した 50 件
ORDER BY t.id;
```

在庫ごとの相関サブクエリにしたのは、行数の推定に左右されず、「1 在庫につき 1 回のインデックス範囲走査」の実行計画にするためである。CTE を使わないので、MySQL 5.7 でも動く。

### A.2 推移グラフ

```sql
SELECT GREATEST(d, :from) AS day, SUM(q) AS amount
FROM (
  SELECT :from AS d, quantity AS q FROM inventory
  WHERE company_id = :company_id AND id = :id
  UNION ALL
  SELECT scheduled_date, quantity FROM purchase_item
  WHERE company_id = :company_id AND inventory_id = :id
    AND status IN ('none', 'before') AND scheduled_date <= :to
  UNION ALL
  SELECT COALESCE(scheduled_date, :from), -quantity FROM delivery_item
  WHERE company_id = :company_id AND inventory_id = :id
    AND status IN ('none', 'before') AND (scheduled_date <= :to OR scheduled_date IS NULL)
) x
GROUP BY 1 ORDER BY 1;
```

`from` 以前の分（現在庫と、日付未定の出庫を含む）は `from` の日にまとめて計上する。

### A.3 インデックスと実行計画

| テーブル | インデックス |
|---|---|
| `purchase_item` | (company_id, inventory_id, status, scheduled_date, quantity) |
| `delivery_item` | (company_id, inventory_id, status, scheduled_date, quantity) |

A.1 の SQL の実行計画（`bench/plans/` の `pg_a1_*.txt`、`mysql_a1_*.txt`）では、両 DB とも、明細はテーブル本体を読まずにインデックスだけで集計していた（PostgreSQL は Index Only Scan で Heap Fetches 0、MySQL は Covering index lookup）。各在庫につき 1 回の範囲走査（loops=50）だった。条件の扱いは次のとおり。

| DB | 明細 | インデックスの検索条件（Index Cond / lookup） | 読んだ行に対する判定（Filter） |
|---|---|---|---|
| PostgreSQL | 入庫 | 会社 ID、在庫 ID、予定日 | status |
| PostgreSQL | 出庫 | 会社 ID、在庫 ID | status、予定日（NULL との OR） |
| MySQL | 入庫 | 会社 ID、在庫 ID | status、予定日 |
| MySQL | 出庫 | 会社 ID、在庫 ID | status、予定日（NULL との OR） |

- どの組み合わせでも、範囲の先頭は会社 ID と在庫 ID で決まる。
- status は範囲の絞り込みに使われていないので、完了済みの明細もインデックス上は読むと考えられる（5 章 L1）。
- PostgreSQL の入庫側では予定日も Index Cond に現れる。ただし、インデックスの列順で status より後ろにあるため、走査範囲そのものを狭めているかはこの計画からは判断できない。

### 方式比較（50 在庫への付与。ページングを除き、条件をそろえたもの。p50 / p95、ms）

| ページ | PostgreSQL 直接集計 | PostgreSQL 事前集計 | MySQL 直接集計 | MySQL 事前集計 |
|---|---|---|---|---|
| 1 ページ目（高密度） | 13.5 / 17.5 | 2.5 / 4.1 | 32.0 / 51.8 | 6.9 / 10.7 |
| 2,001 ページ目 | 0.7 / 1.0 | 0.4 / 0.6 | 1.3 / 1.5 | 1.0 / 1.3 |
| 最終ページ（高密度） | 13.7 / 16.1 | 2.4 / 3.1 | 31.0 / 36.9 | 7.0 / 10.9 |

- 高密度のページでは、事前集計のほうが 4〜5 倍速い。採用判断では、直接集計単体の絶対値と、事前集計の整合性管理コストを比べた。
- 両方式の結果は一致した。

### SQL の形とページングで分かったこと

- 対象在庫と明細を `UNION ALL` で結合してから集計する形は、PostgreSQL の最終ページで対象 50 在庫を 1 件と見誤り、明細の集計を 50 回繰り返した。実行時間は 2.1 秒だった。在庫ごとの相関サブクエリ（A.1）にすると、両 DB で安定した。
- 一覧のページングを OFFSET で 1 文にまとめた場合、MySQL では最終ページの読み飛ばしだけで 136ms（p50）かかった。先に id だけを取って結合する遅延結合では 23ms になった（5 章 L3）。
- 推移グラフ（1 在庫、高密度）は、PostgreSQL で 0.4ms（EXPLAIN ANALYZE の実行時間）。A.2 の累積値が A.1 の値と一致することを、計測データでも確認した（`bench/graph_check.py`）。

計測スクリプトと再現手順は `bench/README.md` にある。

## 付録 C. 事前集計への切り替え

### 切り替え条件

次のいずれかを満たしたら、日別の事前集計への切り替えを検討する。

1. ピーク時の一覧 API の p95 が目標（例：200ms）を超え、原因が明細の集計にある（5 章 U1・U2）。
2. 実データで、未完了の明細が多く、かつ同じ在庫の同じ日付に明細が集中している。
3. 予定フリー在庫数での並べ替えや、欠品予定の在庫での絞り込みが要件になった（5 章 A1）。

### 切り替える場合に必要になるもの

在庫 × 日付の増減テーブルを持ち、`quantity + 指定日までの増減合計` で求める。正しさを保つために、少なくとも次が必要になる。

- 完了時の予定分の取り消しを、4.1 の完了処理と同じトランザクションで行う（非同期だと 15 → 20 → 15 が発生する）。
- 増減が 0 になった行を、同じトランザクションで削除する（使われなくなった日付の行が残り、読み取り量の上限が成り立たなくなる）。
- 反映処理と補正処理は、どちらも在庫の行をロックしてから処理する。
- 導入前からある未完了明細をバックフィルし、全在庫で差異がないことを検証してから切り替える。
- コミットから反映完了までの時間と、最も古い未処理イベントの経過時間を監視する。
